access code 专题：号从哪来

这是街机卡逆向里最核心的问题：卡里的 20 位 access code 和 UID/IDm 到底是什么关系？ 本章用实测数据给出完整答案。

结论先行

问题答案
access code = f(UID)？否，两者无任何推导关系
access code 从哪来？发卡方服务器分配，注册时写入卡内
卡号字符串 = f(IDm)？是，纯本地 3DES（仅 Konami 体系）
decimal(UID) 有什么用？仅私服在无法读取卡数据时的替身方案

证据链

1. 位宽不匹配（数学排除）

  • 20 位十进制 = 约 66.4 bit，实测两码 int(code).bit_length() 均为 66
  • UID/IDm 是 8 字节 = 64 bit，其十进制最多 19-20 位但数值上限 18446744073709551615 （实测 decimal(IDm) 只有 17 位，形如 00085...）
  • 66 bit 的数不可能由 64 bit 的值"十进制变换"而来

2. 前缀跟发行方，不跟 IDm（信息论排除）

  • Konami 发行的卡 → 520... 号段
  • Sega 发行的卡（注册 Konami 时）→ 501... 号段
  • IDm 里不含发行方信息（IDm 由 Sony 烧录，只反映芯片批次）。 一个能区分发行方的号码，必然出自"看得见 DFC 的系统"，即发卡服务器

3. 无本地校验位（结构排除）

  • 两码均不通过 Luhn 校验
  • 码体无可见重复结构
  • 合法性完全依赖服务器数据库背书

4. 相近 IDm → 完全不同的码体（直观排除）

两张卡 IDm 仅中段几个字节不同（012E61... vs 012E59...）， 若存在平滑推导函数，码体应有结构相关性。实际毫无关联。

官方注册流程（重建）

第一次刷卡
   │
   ├─ 读卡器上报 IDm + PMm + DFC
   ├─ 服务器检查对应公司的存储区（如 Konami 查 SPAD0）
   │     └─ 已有合法数据 → 解密取码 → 登录，流程结束
   └─ 无数据（新卡）
         ├─ 按发行方分配新码（520 段自家卡 / 501 段外来卡 ⚠️号段规则为实测归纳）
         ├─ 加密后经读卡器写回卡内
         └─ 建立 码 ↔ 账号 数据库记录

此后每次刷卡：读卡 → 解密 → 取码 → 查库。IDm 只在第一次出现。

私服生态里的三种行为

场景私服做法
卡里有合法 SPAD0读卡器直通读出来，用真码（✅ 本文作者私服即如此）
卡是普通 FeliCa，无 AIC 数据用 decimal(IDm) 补零 20 位当伪码（Aqua 的 FeliCaLookupHandler）
卡是自写 MIFARE Aime读块 2 BCD 取码

撞号风险

自建卡时若凭空编一个 20 位码写进去，只要该码在服务器库里已存在， 就会登录进别人的账号（或产生数据混乱）。自制码应使用不可能冲突的号段 或先在服务器面板确认。
