# Amusement IC 协议

Amusement IC（AIC）是四家厂商的统一卡标准，2021 年落地。
本章基于对多张真卡的完整 dump（PN532 + libnfc），所有块数据均为实测 ✅。

## 物理层

| 项 | 值 |
|---|---|
| 芯片 | FeliCa Lite-S |
| 系统码（syscode） | `0x88B4` |
| 轮询速率 | 212 / 424 kbps |
| IDm 指纹 | 前 2 字节恒为 `01 2E`（Sony AIC 制卡批次） |
| PMm 指纹 | `00 F1 00 00 00 01 43 00` |

实测卡例：

```
IDm: 01 2e 59 39 99 58 94 b0
PMm: 00 f1 00 00 00 01 43 00
SC : 88 b4
```

## 服务码：0x000B 只读，0x0009 读写

AIC 卡上有两个能用的服务码，分工明确 ✅（未发行空白卡实测）：

| 服务码 | 读 | 写 | 说明 |
|---|---|---|---|
| `0x000B` | 用户区 + 系统区全部可读 | 一律 `01 A6` 拒绝 | **只读服务**，读卡器和游戏读卡走这条 |
| `0x0009` | 用户区可读 | 未发行卡写入成功 | **读写服务**，官方写卡走这条 |
| `0x000A` / `0x000D` / `0x0008` | 无响应 | 无响应 | 卡上不存在 |

::: warning 重要更正
本文早期版本写的「只有 0x000B 返回数据」「正版 AIC 卡整体写锁」，
是**只用 0x000B 做写测试**得出的假象。`01 A6` 是服务级拒绝
（这个服务本来就不给写），不等于发行商写锁。
segatools 的官方抓包里，游戏写 FeliCa 用的服务码正是 `0x0009`，与此吻合。
正版发行卡经 `0x0009` 能否写入尚未复验 ⚠️。
:::

Lite-S 不响应 Request Service（0x02）枚举 ✅。

### 用户区块图（0x00-0x0E）

正版发行卡（实测 Konami DFC `0068` / Sega DFC `0078`）：

```
块          用途                       读（0x000B）  写（0x000B）
0x00        SPAD0 Konami e-amusement   明文可读       01 A6
0x01        SPAD1 （Sega 系）          01 B1 拒绝     01 A6
0x02        SPAD2 （Bana 系）          01 B1 拒绝     01 A6
0x03        SPAD3 （Capcom 系⚠️）      01 B1 拒绝     01 A6
0x04        SPAD4 （预留 ⚠️）          01 B1 拒绝     01 A6
0x05-0x0D   自由区，全零               明文可读       01 A6
0x0E        全 FF，用途未知             明文可读       01 A6
```

未发行的空白 AIC 卡（DFC 全零，实测 IDm `012e5524f148573a`）：

```
块          内容                       读            写（0x0009）
0x00        出厂可能是 Type 3 Tag AIB   明文可读       可写 ✅
0x01-0x0D   全零，或被人写过 NDEF       明文可读       可反复擦写 ✅
0x0E        全 FF                      明文可读       可写 ✅
```

- SPAD = 各厂商的专属数据块。**只有 SPAD0 对外明文可读**，
  这是设计使然：任何 AIC 读卡器都能判断"这张卡有没有注册过 Konami"
- 正版卡的 SPAD1-4 连读都要 MAC 认证（密钥在官方读卡器 SAM / 服务器侧）；
  空白卡上这几块毫无保护，说明 **MAC 保护是发行时写进去的，不是芯片出厂特性** ✅
- 空白卡的块 0x00 出厂可能是 NFC Forum Type 3 Tag 的 AIB
  （`10 04` 开头，末 2 字节是前 14 字节之和），块 0x01 起是 NDEF 记录

### 系统区块图（0x80-0x91）

```
块          内容（实测）
0x80        全零（MC / 锁配置区，绝对不要写）
0x81        全零
0x82        IDm(8) + DFC(2) + 补零        ← 识别核心
0x83        IDm(8) + PMm(8)               ← 出厂镜像
0x84        全零
0x85        系统码 88 B4 + 补零
0x86        正版 Sega 卡 00 01，空白卡全零
0x87        全零
0x88        空白卡 FF FF FF 01 07 + 补零   （只做过读）
0x89-0x8F   无响应
0x90        空白卡 0F FE FF + 补零         （只做过读）
0x91        无响应
```

**块 0x82 是卡片身份证**：读卡器读它拿到 IDm 和 DFC。
aic_pico 读卡器固件的识别路径就是 `读 0x000B 块 0x82 → 按 DFC 报卡名`。

## DFC：发行方代码

块 0x82 偏移 8-9 的 2 字节（实测均为 `00 xx` 形式）：

| DFC 低字节 | 发行方 |
|---|---|
| `0x68` | Konami |
| `0x78` | Sega |
| `0x2A` / `0x3A` | Bandai Namco |
| `0x79` | Taito（NESiCA） |

未发行的空白 AIC 卡 DFC 为 `00 00` ✅，这是判断"这张卡从没被任何厂商发行过"
最直接的特征。

## 写保护机制 ⚠️（结论已更正）

早期结论「正版 AIC 卡是只读资产」建立在**只用服务码 0x000B 写**的实验上，
而 0x000B 本身就是只读服务，`01 A6` 属于服务级拒绝。目前确定的事实：

1. `0x000B` 对任何块的写一律 `01 A6`，正版卡和空白卡表现一致 ✅
2. `0x0009` 在未发行的空白 AIC 卡上读写全部成功，可反复擦写、可还原 ✅
3. segatools 官方抓包中游戏写 FeliCa 用的服务码是 `0x0009` ✅
4. 正版发行卡的 SPAD1-4 读返回 `01 B1`（需 MAC），空白卡上同样位置毫无保护 ✅
5. 正版发行卡经 `0x0009` 能否写入：**未复验** ⚠️

::: tip 安全的复验方法
拿正版卡在空白块 `0x0D` 上做"写图案 → 回读 → 还原 → 回读"的可逆测试，
服务码用 `0x0009`。全程不要碰 SPAD0，也不要碰系统块。
:::

::: danger 真正的防伪底线
不是"块写不进去"，而是：

- SPAD1-4 的 MAC_A 体系（随机挑战写块 0x80，同一条命令读 0x82/0x86/0x90/0x91 取 MAC）
- 服务端对 access code 的发号与绑定

MAC_A 的密钥在各厂商非公开体系里，空白卡上算不出来。
:::

## 识别流程（读卡器视角）

把 aic_pico 固件的逻辑抽象出来，一台 AIC 读卡器的判定树是：

```
轮询到卡
├─ FeliCa（syscode 88B4）
│   ├─ 读 0x000B/0x82 → 按 DFC 报发行方
│   └─ 读 0x000B/0x00 → SPAD0 解密 → Konami access code
├─ MIFARE
│   ├─ 免认证读块 0，偏移 10-11 = F8 01 → NESiCA（旧）
│   ├─ KeyA 60 90 D0 06 32 F5 认证块 3 → 读块 1
│   │   └─ 偏移 2-6 = "NBGIC" → Banapassport
│   └─ KeyB WCCFv2 认证块 3 → 读块 1
│       └─ 开头 "SBSD" → Aime
└─ ISO 15693 → 其他
```

## 一张卡通吃四家的原理

AIC 卡不存储"这是哪家的卡"这种状态——它是一张**带多个独立插槽**的卡：

- 第一次在 Konami 游戏上刷 → Konami 服务器写 SPAD0（501/520 号码段）
- 第一次在 Sega 游戏上刷 → Sega 侧建立记录（走 SPAD1 MAC 体系）
- 各家的数据互不可见、互不干扰

所以一张 Sega 发行的 Aime 卡里装着 Konami 的 `501...` access code
是完全正常的（本文实测卡就是如此）。
